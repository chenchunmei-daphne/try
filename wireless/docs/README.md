# docs

本文档用于说明 `wireless-cax` 仓库中 `docs/` 目录的定位、职责边界与使用方式，明确哪些内容应进入 `docs`，以及这些内容在项目协作中的作用。

`docs/` 中的文档用于**约束当前协作与执行行为**，而不是记录探索过程或个人思考。本目录下的文档应保持结构稳定、语义清晰，并能够在较长时间内被团队成员与 AI 系统可靠调用。当前内容处于持续增量修订状态，允许在不破坏既有语义的前提下逐步完善。

## docs 的核心定位

在 `wireless-cax` 项目中，`docs/` 目录承担的是“执行层文档”的角色，其核心目标是回答以下问题：

- 当前项目是**如何被协作推进的**
- 成员在执行阶段**应该遵守哪些共同约定**
- 外部或新加入成员**如何快速理解项目的工作方式与约束**

`docs/` 不追求完整覆盖所有知识，而强调稳定性、可执行性与一致性。

## 与 kb 的职责区分

为了避免文档体系混乱，项目明确区分 `docs/` 与 `kb/` 的职责。

- `docs/`
  - 存放已经形成共识、用于指导或约束当前执行行为的文档
  - 内容应尽量稳定，修改需谨慎，并通过 Issue + PR 进行
  - 典型内容包括：协作协议、接口规范、目录约定、运行说明

- `kb/`
  - 存放认知形成过程与可复用知识资产
  - 允许不完整、探索性、阶段性结论
  - 典型内容包括：模型推导、方案对比、实验记录、失败分析

一般工作流为：探索性内容先进入 `kb/`，当结论稳定并需要对团队行为形成约束时，再整理进入 `docs/`。

## docs 下的目录与文件约定

`docs/` 目录下的每一个子目录或文档，都应有明确的存在理由和使用场景。

当前及规划中的典型内容包括：

- `docs/README.md`
  - 本文件，用于说明 `docs/` 目录本身的定位与使用方式

- `docs/collaboration/`
  - 项目协作协议
  - 明确团队成员之间、以及团队与 AI 之间的协作方式与责任边界

- `docs/context/`
  - 项目事实层上下文
  - 存放当前被视为事实的全局信息，用于快速同步团队认知，以及作为大语言模型的最小可信上下文输入
  - 内容要求简洁、低歧义、避免推断

- 其他可能的文档类型
  - 项目级技术路线与阶段目标说明
  - 稳定接口与数据格式约定
  - 环境、依赖与最小可运行链路说明

是否新增文档或子目录，应以“是否对当前执行阶段形成明确约束”为判断标准。

## 文档写作与维护原则

`docs/` 下的文档需遵循以下基本原则：

- 面向长期维护，而非一次性交付
- 面向团队整体，而非个人笔记
- 面向人类读者与 AI 系统的双重理解
- 明确表达约束、假设与边界，避免模糊指令

在写作风格上，应优先使用自然语言与清晰结构，避免修辞性表达和不必要的格式复杂度。

## 修改与演进方式

对 `docs/` 的任何修改，都被视为对项目协作规则或执行约束的调整，应谨慎对待。

基本约定如下：

- 所有修改必须通过 Issue 提出动机与背景
- 通过 PR 进行审查与合并，避免直接修改主线
- 修改应尽量保持向后兼容，避免频繁破坏既有约定

当规则本身不再适用时，应明确说明变更原因，而不是隐式替换。

## 新成员的使用建议

新成员进入项目后，建议优先阅读以下内容：

1. `docs/README.md`，理解文档体系的角色划分
2. `docs/collaboration/README.md`，理解协作方式与基本约定
3. 结合 Issue 列表，理解当前项目所处阶段与重点

在未完全理解算法与代码细节之前，遵循 `docs/` 中的协作与执行约定，是参与项目的最低要求。

## 结语

`docs/` 的价值不在于数量，而在于其是否能够在关键时刻为团队提供清晰、一致的行动依据。

当文档无法被执行、无法被复用或无法被信任时，其存在本身就应被重新审视。`docs/` 的演进应始终服务于协作质量与项目长期可持续性。
