# Collaboration

本文档用于说明 `wireless-cax` 项目在执行阶段的协作协议，明确团队成员之间、以及团队与 AI 之间的协作方式与责任边界。

该文档的目的不是描述理想状态，而是为当前与未来的实际协作提供一套**可执行、可检查、可演进**的共同约定。本文档处于持续增量修订状态，任何修改必须通过 Issue + PR 方式完成。

## 协作目标与基本立场

`wireless-cax` 是一个长期内部能力建设项目，其协作目标可以概括为三点：

- 支持多人并行推进研究、文档与工程实现
- 保证所有成果可追溯、可评审、可继承
- 为团队协作与 AI 协作同时提供稳定边界

在本项目中，
* 协作优先级高于个人效率
* 工程留痕优先于即时沟通
* 长期可维护性优先于短期便利。

## 项目背景与当前阶段

`wireless-cax` 统一承载算海团队在无线通信 CAX 方向的内部能力沉淀，当前主要来源于以下两类在研项目：

- 信道矩阵建模与重构相关研究与工程实现
- 天线频域电磁仿真中的高阶与自适应有限元算法研究

项目当前处于执行与沉淀并行阶段，重点不在于频繁推翻既有设计，而在于：

- 将已有研究成果工程化、模块化
- 明确接口、约束与协作边界
- 通过文档与测试确保成果可被他人复用

## 基本协作工作流

本项目统一采用 Issue + PR 作为最小协作闭环。

- Issue 是一切工作的正式起点
- PR 是一切成果进入主线的唯一方式
- 没有 Issue 对应的工作，不视为项目工作

任何任务，无论是代码、文档、调研还是规范调整，都必须能够在 Issue 中找到来源，并在 PR 中完成交付。

## 仓库级协作模式说明

本项目不采用 fork 仓库的协作方式。

所有成员直接在 `wireless-cax` 主仓库中协作，通过分支隔离具体工作内容。这样做的目的在于降低协作复杂度，并确保所有上下文、讨论与历史记录集中存放。

### 分支基本约定

- 所有工作分支从 `develop` 分支拉出
- 推荐使用清晰、短小且有语义的分支名，例如：
  - `feature/xxx`：功能、算法或结构性新增
  - `fix/xxx`：问题修复
  - `doc/xxx`：纯文档相关工作
  - `research/xxx`：探索性实现或验证

### PR 基本约定

- 所有 PR 提交目标为 `develop` 分支
- 每个 PR 必须关联至少一个 Issue
- 一个 PR 只解决一个明确问题，避免混合无关修改

`develop` 分支代表当前可协作、可继续推进的稳定主线，是否合并到 `main` 由项目阶段统一决定。

## Issue 与即时沟通的边界

Issue 是唯一正式的工程入口，即时沟通工具仅用于辅助协同。

当出现问题或需求时，推荐流程为：

1. 先创建或补充对应 Issue，明确问题背景与目标
2. 再通过即时沟通工具提醒相关人员，并附上 Issue 链接

即时沟通工具适用于提醒、协调顺序和简要同步状态，但不应替代 Issue 承担工程记忆。

基本原则是：即时沟通解决“现在怎么办”，Issue 解决“以后如何复盘与复用”。

## docs 与 kb 的职责边界

为避免文档失序，项目对 `docs` 与 `kb` 的职责做如下区分：

- `docs/`
  用于存放已经形成共识、用于约束当前执行行为的文档，例如协作协议、接口规范、运行说明。这些内容默认具有一定稳定性。

- `kb/`
  用于存放认知形成过程，包括方案探索、推导记录、对比分析与失败经验。这里允许不完整、不确定与演进。

一般原则是：探索性内容先进入 `kb`，当结论稳定并需要约束行为时，再整理进入 `docs`。

## 与 AI 协作的基本约定

### AI 的适用范围

在本项目中，AI 被视为协作工具而非责任主体。鼓励使用 AI 辅助以下工作：

- 拆解任务、分析依赖与潜在风险
- 撰写文档或代码的初稿
- 提出接口设计、模块划分与测试建议
- 规范化 commit message 与 PR 描述

所有 AI 产出都应被视为“建议”，而非直接成立的工程事实。

### AI 的使用边界

以下行为在本项目中被明确限制：

- 将未经验证的 AI 推断直接写入 `docs`
- 绕过 Issue + PR 流程直接修改主线内容
- 将评审责任转移给 AI

当对 AI 产出的正确性存在疑问时，应优先记录在 `kb` 中，而不是直接进入 `docs`。

### 推荐的 AI 协作流程

一个推荐且可控的流程如下：

1. 人工创建 Issue，明确目标与约束
2. 使用 AI 辅助细化 Issue 或提出方案
3. 在分支中由人工主导实现，AI 辅助
4. 使用 AI 辅助规范化 commit 与 PR 描述
5. 通过 PR 完成人工评审与合并

## Commit 作为设计节点的要求

在本项目中，commit 被视为“设计节点”，而不仅是代码快照。

每一个 commit 应能够回答以下问题：

- 解决了什么具体问题
- 引入了什么新的设计决策或约束
- 如何验证其正确性或安全性

推荐使用清晰的 commit message 结构，以便未来回溯与分析。

## 对新成员的最低期望

新成员进入项目后，建议按以下顺序熟悉环境：

1. 阅读本协作说明，理解协作边界
2. 阅读 `docs/README.md` 与 `kb/README.md`
3. 从 Issue 列表中认领明确任务
4. 在分支中完成工作，并通过 PR 提交

不要求一开始理解所有算法与工程细节，但要求遵守协作规则，并保证工作可追踪、可评审。

## 结语

`wireless-cax` 是一个长期项目，其成功依赖于协作结构的稳定性，而不是个别成员的短期投入强度。

清晰的协作协议，是工程质量、研究质量与团队可持续性的共同基础。当规则需要调整时，应通过 Issue 提出，并在达成共识后更新本文档。
