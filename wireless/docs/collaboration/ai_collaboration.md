# 与 AI 协作的工作约定

本文档用于约束 `wireless-cax` 项目在执行阶段与 AI（包括但不限于大语言模型、代码补全工具、自动化分析工具等）的协作方式，明确 AI 的适用边界与责任划分，确保 AI 成为**可控的生产力工具**，而不是引入认知偏差与工程风险的来源。

本文档属于执行期协作规范的一部分，适用于代码、文档、调研与项目管理等所有工作内容。其目标不是限制使用 AI，而是为“如何正确使用 AI”提供稳定、可继承的共识。

## 协作目标与基本立场

在 `wireless-cax` 项目中，与 AI 协作的核心目标包括：

- 提升任务拆解、设计与实现的效率
- 提升文档、代码与接口的规范性与一致性
- 保证所有工程产出可评审、可回溯、可维护

在此基础上，项目明确以下基本立场：

- AI 可以加速思考、表达与整理，但不能替代工程责任
- AI 的所有产出都必须能够被人类成员理解、验证与评审
- 所有正式交付仍以 Issue + PR 为唯一有效载体

## AI 的适用范围

在本项目中，鼓励在以下场景中合理使用 AI 进行协作。

### 任务拆解与风险识别

AI 可用于辅助将复杂目标拆解为可执行的工作单元，包括：

- 将一个较大的研究或工程目标拆分为多个可并行推进的 Issue
- 梳理任务之间的依赖关系与执行顺序
- 提前识别潜在风险、技术不确定点与回退策略

AI 在此阶段的角色是“结构化助手”，而不是决策者。

### 文档与规范输出辅助

AI 可用于提升文档产出的效率与一致性，例如：

- 生成 `docs/` 或 `kb/` 文档的初稿与结构化框架
- 将零散讨论整理为可维护的 Markdown 文档
- 辅助生成接口确认清单、追问清单或对外沟通要点

所有文档最终内容必须由人工确认其事实性与适用性。

### 代码结构与接口设计辅助

在代码层面，AI 可用于辅助思考与表达，包括：

- 提出模块边界、接口定义与数据结构候选方案
- 给出伪代码、流程描述或单元测试设计建议
- 辅助识别可能存在的 silent wrong 风险点

AI 的建议不能直接等同于正确设计，必须结合项目上下文与人工判断。

### 提交信息与 PR 文案规范化

AI 可用于辅助规范工程输出的表达形式，例如：

- 根据实际改动内容生成规范的 commit message
- 协助整理 PR 描述，包括背景、变更点、验证方式与风险说明
- 辅助生成 code review checklist

在本项目中，每一个 commit 都被视为一个“设计节点”，而不是简单的存档点。其设计意图与验证方式必须清晰可读。

## AI 的使用边界与禁止行为

为避免不可控风险，项目对 AI 的使用设定明确边界。

### 禁止未经验证的事实注入

以下行为在本项目中被明确禁止：

- 将 AI 的推断或臆测当作项目事实写入 `docs`
- 将 AI 生成的公式、数据或结论直接作为工程依据
- 引用外部标准、论文或资料而不注明来源与可追溯性

当某一结论尚未被验证时，应优先写入 `kb`，而不是进入执行性文档。

### 禁止绕过工程流程

AI 不能成为绕过协作流程的工具，具体包括：

- 不经 Issue 就开展大规模修改
- 直接合并大量 AI 生成代码而不做测试与验证
- 在即时沟通工具中形成结论却不落到 Issue、文档或 PR 中

所有工作仍需遵循既定的工程与协作流程。

### 禁止替代人工评审责任

AI 可以辅助 review，但不能替代 review。

任何 PR 的责任人必须能够清楚说明：

- 为什么要进行这次修改
- 修改影响的范围与边界
- 如何验证修改的正确性或安全性

评审责任始终由人类成员承担。

## 推荐的 AI 协作工作流

在执行层面，推荐采用以下可控的 AI 协作流程。

### 从 Issue 开始

在开展任何任务前：

1. 由人工创建 Issue，明确目标、产出路径、完成标准与时间盒
2. 使用 AI 辅助完善 Issue 内容，例如拆解步骤、补充风险点与验收标准

### 实现与提交阶段

在实现过程中：

- 由人工主导设计与实现
- 使用 AI 辅助表达、结构化设计与发现潜在问题
- 关键假设、接口语义与结论按职责写入 `kb` 或 `docs`

在提交阶段：

- 先由提交者自己总结变更要点
- 再使用 AI 辅助规范化 commit message 与 PR 描述
- 最终由提交者确认并承担全部责任

### PR 评审阶段

PR 描述应至少包含以下信息：

- 关联的 Issue
- 变更范围与影响说明
- 验证方式与验证结果
- 已知风险与必要的回退方式

AI 可以辅助检查表达完整性，但不能替代评审判断。

## Commit 作为设计节点的要求

在 `wireless-cax` 项目中，commit 被视为工程演进中的设计节点。

每一个 commit 都应能够回答以下问题：

- 解决了什么具体问题
- 引入了什么新的设计决策或约束
- 如何验证其正确性，或至少确认未破坏既有行为

推荐保持 commit 粒度可评审、可回溯，避免将大量无关改动混合在一次提交中。

## 输出归档与信息安全约束

在与 AI 协作过程中，需特别注意以下约束：

- 不向 AI 提供包含敏感信息的甲方数据、模型文件或日志
- 对外沟通材料与结论需经过项目负责人确认
- 重要假设、接口语义与约束必须沉淀到 `docs`，并保持可追溯

## 结语

在 `wireless-cax` 项目中，AI 的正确角色是：

- 帮助团队更快拆解问题
- 帮助团队更清晰表达决策
- 帮助团队更规范地产出工程成果

但工程质量、事实判断与最终责任始终属于团队成员与评审流程。当对 AI 产出的可信度存在疑问时，应优先记录在 `kb`，而不是直接进入 `docs`。
