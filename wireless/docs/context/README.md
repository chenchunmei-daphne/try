# context

本文档用于说明 `wireless-cax` 项目中 `docs/context/` 目录的整体设计目标、分级结构与使用方式。

`context/` 的定位是**项目事实层上下文（facts-only
context）**：为项目成员与大语言模型提供一组“当前可以被认为是事实”的最小集合，用于快速建立全局认知、避免背景误解，并降低
AI 辅助过程中出现 silent wrong 的风险。

本目录中的内容以“当前有效”为准，而非历史记录或推理结论。

## context 的核心目标

`docs/context/` 解决的不是“解释问题”，而是“对齐事实”。其核心目标包括：

- 为新成员提供快速、低歧义的项目全局认知入口
- 为不同 AI 辅助场景提供可控、可裁剪的上下文输入
- 明确区分哪些信息是事实，哪些应进入规则或推理层

在任何情况下，`context` 都不承担论证、推理或方案比较的职责。

## context 与 docs、kb 的职责边界

为了避免信息混杂，项目对三类文档的角色作出明确区分：

- `docs/context/`
  - 项目事实层上下文
  - 存放当前被视为事实的稳定信息
  - 面向快速阅读、快速复制给 AI 使用

- `docs/`
  - 执行与协作规则层
  - 存放用于约束行为、接口与流程的规范性文档

- `kb/`
  - 认知与推理层
  - 存放推导、探索、对比分析与阶段性判断

基本原则是：
事实进入 `context`，规则进入 `docs`，推理与探索进入 `kb`。

## context 的分级设计原则

`context` 采用分级设计，以适配不同人类与 AI 使用场景。分级的基本原则包括：

- 每一级只包含一种稳定性层级的事实
- 每一级文件都可以被独立使用，不依赖隐含前文
- 文件名本身应清晰表达其事实对象与边界
- 严禁在 context 中引入推理性、假设性或争议性内容

分级的目标不是“更复杂”，而是**让上下文输入可控、可裁剪、可复用**。

## context 的分级结构说明

当前推荐的 `docs/context/` 目录结构如下：

```text
docs/context/
├── README.md
├── level0_project_identity.md
├── level1_project_stage.md
├── level2_project_constraints.md
├── level3_project_operations.md
└── tasks/
    └── README.md
````

各层级的职责如下。

### Level 0：项目身份事实

* 文件：`level0_project_identity.md`
* 内容范围：

  * 项目是什么、不是什么
  * 项目在算海体系中的位置
  * 长期不变的目标与边界
* 稳定性：最高
* 典型用途：

  * 新成员快速了解项目本质
  * 向 AI 提供最小稳定身份上下文，防止方向性偏差

### Level 1：当前阶段事实

* 文件：`level1_project_stage.md`
* 内容范围：

  * 当前所处阶段
  * 当前阶段的核心目标与非目标
  * 阶段性已确认事实
* 稳定性：阶段性稳定
* 典型用途：

  * 方案讨论
  * 任务拆解
  * 技术路线沟通

### Level 2：硬约束与不可违反事实

* 文件：`level2_project_constraints.md`
* 内容范围：

  * 已冻结的技术假设
  * 不可违反的接口或工程约束
  * 明确禁止的行为或路径
* 稳定性：中高
* 典型用途：

  * AI 辅助代码生成
  * 接口与模块设计
  * 防止 silent wrong 的关键上下文

### Level 3：协作与操作事实

* 文件：`level3_project_operations.md`
* 内容范围：

  * 仓库结构的事实描述
  * 当前采用的协作方式与工作流事实
  * 文档体系的职责分工事实
* 稳定性：中等
* 典型用途：

  * AI 生成 Issue、PR 或提交说明
  * 新成员快速进入协作状态

本层只描述“当前如何运作”的事实，不重复协作规则本身。具体规则以 `docs/collaboration/` 为准。

### Level 4：任务级上下文（可选）

* 目录：`docs/context/tasks/`
* 内容范围：

  * 针对单一任务或 Issue 的局部事实快照
* 稳定性：低，生命周期短
* 典型用途：

  * 深度技术实现
  * 长上下文 AI 对话
  * 临时 agent 使用

任务级 context 建议与 Issue 编号或明确主题绑定，完成后可归档或删除。

## 面向 AI 的使用建议

为降低 AI 辅助时的上下文噪声，建议项目成员按场景选择最小必要 context 组合：

* 项目介绍、方向判断：Level 0
* 方案与任务拆解：Level 0 + Level 1
* 代码与接口设计：Level 0 + Level 1 + Level 2
* PR / Issue / 流程相关：Level 0 + Level 3
* 深度任务实现：在上述基础上增加对应的 task context

避免将所有 context 一次性输入给 AI。

## 修改与维护约定

由于 `context` 内容会直接影响团队决策与 AI 输出，其维护需遵循以下约定：

* 所有新增或修改必须通过 Issue 提出
* Issue 中需说明事实变化或认知修正的原因
* 通过 PR 合并，保持变更可追溯

当某一事实不再成立时，应及时更新对应文件，而不是依赖口头或隐式约定。

## 结语

`docs/context/` 的价值不在于信息量，而在于它是否为人类与 AI 提供了一个**共同、可靠的事实起点**。

在项目复杂度不断上升的情况下，维护好 context，往往比增加更多说明性文档更重要。
